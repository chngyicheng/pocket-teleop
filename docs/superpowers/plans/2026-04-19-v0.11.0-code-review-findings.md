## Logic Issues

### L1 — `video_source.ts:97` — `apply()` 傳入未 trim 的 `url` 至 `save()` / `buildMtxSource()`

`validate()` 內部做 `url.trim()` 驗證，但 `apply()` 直接把原始 `url`（未 trim）傳給 `save()` 和 `buildMtxSource()`。若調用方傳入有前後空格的 URL，儲存至 localStorage 的值和發給 MediaMTX 的值都會帶空格。

UI 層 `index.html:1042` 已做 `videoUrlInput.value.trim()`，故從瀏覽器操作路徑安全；但程序化調用 `picker.apply('rtsp', ' rtsp://cam:554 ')` 不走 UI，會靜默存入帶空格的 URL。

**修復建議**：`apply()` 開頭加 `url = url.trim()`，或 `save()` / `buildMtxSource()` 各自 trim。

---

### L2 — `video_source.ts:107` — `onMjpegUrl(null)` 在 fetch **之前**觸發；fetch 失敗後 UI 狀態不一致

非 MJPEG 模式下，`onMjpegUrl?.(null)` 在 fetch 發出前調用。若 fetch 失敗（HTTP error / network error），MJPEG 圖像已被清除，但 MediaMTX 路徑未切換成功——用戶看到空白視頻面板，實際源沒變。

**是 bug 還是可接受行為**：取決於設計意圖。若視 "清除 MJPEG 顯示" 為 "開始切換" 的 optimistic UI，可接受但應有回退。若希望只在成功後清除，應將 `onMjpegUrl?.(null)` 移至 `if (res.ok)` 內。

---

### L3 — `index.html:948` — `videoStatus` 恆為 `null`（元素不存在）

```js
const videoStatus = document.getElementById('video-status');
```

HTML 中無 `id="video-status"` 元素（設置抽屜中為 `id="video-source-status"`）。`showVideoStream` 和 `hideVideoStream` 中的 `if (videoStatus) videoStatus.textContent = ...` 永遠不執行——"Connected" / "Not available" 文字靜默丟棄。這是死代碼路徑。

### L4 — `index.html:950-955` — `showVideoStream()` 不隱藏 `mjpegImg`；WhepClient 重連時雙流疊加

```js
function showVideoStream(stream) {
  videoEl.srcObject = stream;
  videoEl.style.display = 'block';       // 顯示 videoEl
  videoPlaceholderBox.style.display = 'none';
  // mjpegImg 未隱藏！
}
```

若 MJPEG 模式激活時 WhepClient 重連觸發 `onStream`，`videoEl` 會顯示在 `mjpegImg` 之上（或並排），兩個視頻流同時可見。

**修復建議**：`showVideoStream()` 加 `mjpegImg.style.display = 'none'; mjpegImg.src = '';`。

---

### L5 — `video_source.ts:17-21` — `buildMtxSource('mjpeg')` 靜默返回 `{ source: 'publisher' }`

```js
if (mode === 'rtsp' || mode === 'udp' || mode === 'srt') return { source: url };
if (mode === 'disabled') return { source: 'redirect', sourceRedirect: 'mediamtx-void' };
/* ros2 */               return { source: 'publisher' };
```

`mjpeg` 落至 `/* ros2 */` 分支，返回 `{ source: 'publisher' }`。運行時 `apply()` 對 mjpeg 提前返回，不調用 `buildMtxSource()`，故無實際 bug；但直接調用 `buildMtxSource('mjpeg', ...)` 的外部調用方會得到語義錯誤的結果，且注釋 `/* ros2 */` 具誤導性。

### C2 — `video_source.ts:49` — `loadSaved()` 返回 `rtspUrl` 字段，對 UDP/SRT 語義混淆

```ts

```

UDP/SRT URL 同樣以 `rtspUrl` 返回，調用方需知道此字段包含 rtsp/udp/srt 三種協議的 URL。可改為 `streamUrl` 或 `urlForMode`。

```ts
import { ..., type VideoSourceType } from '../src/video_source.js';
```

整個測試文件未使用此類型，可移除。

---

### C4 — `video_source.test.ts` — 斷言風格不一致

RTSP 錯誤信息用精確 `.toBe('RTSP URL is required.')`，UDP/SRT/MJPEG 用 `.toMatch(/required/i)`。同一模塊同類型斷言風格不統一。
